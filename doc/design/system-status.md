# 系统状态(概览页)

取代原来 State 的监控显示。代码在 `app/UnifiedTools/Status/`:

- `SystemStats.swift`:各项数据的采集函数
- `SystemMonitor.swift`:每 2 秒采样一次,保存最近 60 次的历史
- `SystemStatusView.swift`:概览页界面

主窗口左边栏现在是:**概览**(本页)、**操作**(原来概览里的快捷操作和权限检查)、应用管理、设置。

## 显示的内容

页头显示芯片型号、机型、核心数、内存容量、macOS 版本、已开机时间。下面是卡片:

| 卡片 | 内容 |
|---|---|
| 处理器 | 总占用百分比、用户和系统占比、最近一分钟曲线 |
| 内存 | 已用 / 总量、应用、联动(wired)、压缩三段占比条、曲线、内存压力、交换用量 |
| 存储 | 启动盘已用、可用、总量。"可用"用的是访达同款口径(含系统可清除的空间) |
| 温度 | 处理器核心最高和平均温度、电池温度、固态硬盘温度、系统散热状态 |
| 网络 | 下载和上传速度、两条曲线(Wi-Fi 与有线合计) |
| 图形处理器 | 占用百分比和曲线,没有该数据的机器不显示 |
| 电池 | 电量、充电状态、剩余时间、最大容量、循环次数、适配器功率,台式机不显示 |

只有打开概览页时才采样,离开页面或关闭窗口就停止,所以不会在后台耗电。

## 数据来源

| 项 | 来源 |
|---|---|
| CPU | `host_statistics`(`HOST_CPU_LOAD_INFO`)两次采样的差 |
| 内存 | `host_statistics64`(`HOST_VM_INFO64`);已用 = 应用 + 联动 + 压缩,和活动监视器同口径;交换和压力来自 `sysctl` |
| 存储 | `URLResourceValues` 的总容量和 `volumeAvailableCapacityForImportantUsage` |
| 网络 | `getifaddrs` 里 `en*` 接口的 32 位字节计数,用环绕减法算差 |
| GPU | IORegistry 里 `IOAccelerator` 的 `PerformanceStatistics` |
| 电池 | `IOPS` 加 `AppleSmartBattery`;新系统把容量放在 `BatteryData` 字典里 |
| 温度 | IOKit 的 HID 温度传感器(未公开头文件的符号),不需要管理员权限。取名字含 `tdie` 的作为核心温度,`tcal` 是校准读数,不算 |
| 散热状态 | `ProcessInfo.thermalState` |

## 在本机上实测的读数(开发时核对)

M5 芯片,CPU 约 15%,内存已用 12.1 GB / 16 GB(应用 5.2、联动 2.6、压缩 4.3),存储可用约 138 GB / 494 GB,GPU 32%,电池 94%、循环 90 次,44 个温度传感器(核心约 28°C,电池约 24°C,固态硬盘 26°C)。与活动监视器的口径一致。

## 点开详情:进程排行、内存讲解、泄漏检测

概览页的 **处理器**、**内存**、**网络** 三张卡片可以点击(右上角有小箭头),点进去有「‹ 概览」返回。代码在 `ProcessMonitor.swift`、`ProcessSampler.swift`、`ProcessListView.swift`、`MemoryDetailView.swift`、`LeakDetector.swift`。

### 进程排行(处理器 / 网络 / 内存都用同一个列表)

- 按应用汇总:一个应用的所有辅助进程加在一起(比如 Chrome 的几十个 Helper),显示"N 个进程"
- 列:名称、处理器、内存、下载、上传;点表头换排序;可搜索;默认隐藏 macOS 系统进程(处理器超过 5% 的仍会显示)
- 右边的"退出"按钮:普通应用是"退出"(请求应用自己退出,它会提示保存)和"强制退出…"(确认后直接杀,没保存的会丢);命令行工具和后台程序是"结束进程…"(确认后发 SIGTERM)
- 没有自己窗口的后台进程会显示**中文名和一行说明**(`ProcessDescriptions.swift` 里收录了常见的几十个,如 iOS 模拟器服务、Metal 着色器编译、Spotlight 索引、网页内容进程等);没收录的按位置猜(开发工具、Homebrew、系统服务、你目录里的程序)。名称过长时中间省略,鼠标悬停会显示完整进程名、说明、路径和进程号
- 系统自带的进程和本应用自己带锁,不提供退出
- 采样:UnifiedTools 运行期间每 30 秒在后台记一次(为了泄漏检测);打开详情页时加快到每 2 秒

### 数据来源

| 项 | 来源 |
|---|---|
| 进程内存 | `proc_pid_rusage` 的 `ri_phys_footprint`,和活动监视器的"内存"一列同口径 |
| 进程处理器 | 同一接口的用户加系统 CPU 时间,两次采样相减再除以时间;单核 100%,多核可超过 100% |
| 按应用汇总 | 用 `proc_pidpath` 取可执行文件路径,归到最外层的 `.app`;不在 `.app` 里的按进程名各自成一项 |
| 进程网络 | `/usr/bin/nettop -P -d -L 2`,不需要管理员权限。nettop 在输出不是终端时会缓冲,常驻运行几十秒都没有输出,所以改成每次只跑两个采样就退出,取第二个。打开网络详情页约 2 到 4 秒才出第一批数据 |

### 内存页:怎么看、有没有问题、怎么办

- 顶部**结论卡片**:根据内存压力和交换空间给一句人话判断(绿色健康、黄色紧、红色很紧、或"现在正常但曾经吃紧"),并强调"用了很多内存本身不是问题"
- **内存都花在哪**:应用、联动、压缩、缓存文件、空闲五段占比条,每项都有一句解释。压缩内存会显示"原本多大、压成多大"。另有交换空间、压缩节省、内存压力
- 可用内存 = 空闲 + 缓存文件(缓存在需要时会被立刻丢掉)
- **占内存最多的应用**:带退出按钮的排行
- **"看不懂?"折叠说明**:为什么总是满的、内存压力、压缩、交换、联动内存、什么是泄漏、泄漏和正常增长怎么区分、为什么不能加内存

### 疑似内存泄漏(重点说明局限)

macOS 没有办法从外面直接判断某个程序"泄漏"。这里用的是**行为推断**:长时间记录每个应用的内存,找出"一直涨、从不回落"的。流程见 `LeakDetector.analyze`:

1. 每个内存超过 80 MB 的应用,每约 25 秒记一个点,保留 6 小时;只看最近 3 小时
2. 至少 12 个点,且覆盖至少 30 分钟才下判断(刚启动时的内存上涨和泄漏长得一样,所以必须观察够久)
3. 最小二乘直线斜率(每小时涨多少 MB)、首尾平均值的差、拟合优度 R²、逐点"不下降"的比例
4. **只要中间出现过超过 12% 的大回落就不算**,因为泄漏的程序不会还内存
5. 判定:"很可能在泄漏" = 每小时涨 100 MB 以上、总共涨 250 MB 以上、80% 以上的点不下降、R² 不低于 0.6;"需要留意" = 每小时 40 MB、总共 100 MB、70%、R² 0.5。都达不到就不报

对每个怀疑对象给出**处理办法**(按效果排序):先退出重开(泄漏的内存随进程结束全部还给系统);多进程应用提示先关标签页、关扩展再看(进程数在增加时会特别标注"可能只是开了更多标签页");更新到最新版;重启后很快又涨回来就是应用本身的问题,向开发者反馈或换软件;进一步确认用 `leaks <pid>` 命令(界面里有"复制检查命令"按钮)或 Instruments 的 Leaks。每个怀疑对象下面有"退出这个应用""强制退出…"按钮。

**局限**:
- 这是"疑似",不是定论。缓存型增长(如 Xcode 索引、浏览器缓存)只要没回落,也可能被标出来
- 历史只存在内存里,UnifiedTools 退出或重启后重新开始记。所以要让它一直在后台(它会开机自启)
- 每个应用记录的是它所有进程的合计,看不出是哪个进程在涨
- 只能读到当前用户有权限读的进程

用合成数据验证过判定逻辑:稳定每小时涨 200 MB 判为"很可能",每小时涨 60 MB 判为"需要留意";平稳波动、每小时 15 MB 的缓慢漂移、涨了又整体回落(垃圾回收)、锯齿状缓存、只有 20 分钟数据、涨完就停住,这些都不会误报。

## 没有做的

- **风扇转速**:要读 SMC,需要私有接口;无风扇机型(如 MacBook Air)本来就没有
- **蓝牙设备电量**、**每核心占用**、**占用资源最多的进程**
- **功耗**(瓦数):`powermetrics` 需要管理员权限
- 菜单栏里常驻显示数值(原 State 的主要形态)。现在只在主窗口概览页里看

## 已知限制

- 温度用的是 IOKit 里没有公开文档的符号,系统升级后可能失效;失效时温度卡片只剩电池温度和散热状态,不会崩溃
- 网络速度是接口计数的差值,不区分应用,也不含 VPN 隧道本身的流量重复计算(只统计 `en*` 物理接口)
- 内存"已用"口径和第三方工具可能有几百 MB 差别
